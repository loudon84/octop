## 功能实现边界

本地已确认的兼容缺陷：全局安装的知识 composer 在服务端 required map 为空时仍注册准备器，首条普通消息会被当作企业回合，因空知识库选择而拒绝。依据 `useChatSend.ts` 的全局 capture→bound 分支及 `Composer.tsx` 的空选择拒绝；已接受 proposal 明确要求普通聊天兼容。这与远端现场是否同一根因仍待确认。

选定最小方案：**在 enterprise-knowledge 自己的 composer surface 入口判断是否参与该专家/线程**。使用 Host 已提供的通用 readiness，不修改通用 Host 对其它可选 composer 的行为，不改后端 admission。仅在该 scope 的已认证 required map 包含 enterprise-knowledge 时挂载实际 Composer；明确空 map 时不挂载、不注册准备器、不读写企业 session。初次 readiness 未知不参与；同 scope 后续轮询 loading/error 保留最近已确认的挂载状态，避免定时检查卸载草稿或确认框；发送仍由 Host fresh readiness 拒绝错误/不可用。真实 generation/agent/thread/auth 变化由现有 PluginSurface key 隔离。

功能白名单：`plugins/enterprise-knowledge/ui/src/index.ts`、`host.ts`；如必要可另建同目录小型 composer 入口组件。回归白名单：该 UI 的 `index.test.tsx` 和 Dashboard 的 `enterpriseComposerIntegration.test.tsx`。类型需要兼容既有未消费 readiness 的 settings/tool fixture，不批量改写无关测试。构建只更新插件 UI dist，不修改 Dashboard 生产代码和构建产物。

先 RED：全局插件已安装、服务端无绑定 required map 为空，实际 setup/PluginSurface/原生输入/useChatSend 的首条普通消息应创建一次原生线程并发送，不调用企业 action、不带企业 plugin_context。再 GREEN，并覆盖 required map 非空仍执行准备/空选择仍阻塞、同 scope loading/error 不丢草稿、真实 scope 变更隔离。最终由控制器 review 与执行一次相应类型/构建检查，不重复全仓测试。

- Host：只处理通用专家/线程目标、readiness 状态和提交过程，不引入 WeKnora 字段。
- 插件：只处理自身知识设置、会话准备和用户提示，不自行创建原生聊天线程。
- 未配置/权限不足必须有明确反馈，不通过默认扩大授权解决。
- 若是远端版本或配置不匹配，交付针对性部署/配置步骤，不能声称本地代码修复已在远端生效。

## 服务器先检查的部署条件

截图的插件管理页为“共 1 个插件”，只有 `enterprise-knowledge`。当前 `plugins/enterprise-knowledge/main.py` 的服务依赖声明和 `enterprise-policy` 的策略检查都要求 knowledge/policy **两个 0.1.0 插件**。这能确认截图中的部署清单不完整，但不能单凭它解释 readiness 为何持续 loading。

企业知识使用前应依次确认：

1. 安装并全局启用 `enterprise-knowledge` 与 `enterprise-policy`；目标专家也应允许两者，重新加载/启动专家使策略实际进入运行时。
2. 已有可运行专家和可用模型，聊天已选中该专家；全局插件安装不会替代创建专家。
3. 管理员在知识插件设置保存企业 connection、正确 tenant 和 Key，诊断/发现知识库并保存 allowed KB 白名单。
4. 给实际聊天用户保存显式员工 grant；管理员使用聊天也不能依赖“管理员自动读全部库”的假设。
5. 为目标专家保存启用的企业绑定、专家允许库和至少一个默认授权库。未配置联网供应商时先只用 KB_ONLY，不把 WEB_ONLY 当成无配置回退。
6. 返回聊天，刷新插件模块后验证：无企业绑定的普通专家应能发普通消息；企业绑定专家必须在权限/选库齐备后创建真实线程、准备 operation 再提交。

仍持续显示 loading 时，在报错浏览器记录 `/api/agents`、`/api/plugins`、`/api/plugins/requirements?agent_id=...`、插件 UI entry、原生线程创建和 `session.get/save`、`operation.prepare` 的状态与顺序。404 优先核对服务器 Octop 是否含该分支 Host API；401/403 检查当前登录及权限；pending 核对服务端日志/代理。仅提供脱敏状态与首条异常，不回传认证 headers 或完整文档数据。
