Read-only trace of current source paths. “Identity” below means an authenticated Octop user, not merely a numeric ID on an inbound message or a harness request.

## Dashboard entry paths

- Local dashboard WebSocket resolves the query token with `resolve_user_from_token` before accepting turns (`src/octop/api/routers/chat/ws.py:37-57`). It also checks agent access (`:68-75`). Every `user_turn`, including busy turns steered into the active queue, is parsed and passed through `prepare_dashboard_turn` with that resolved `user` (`:190-225`). That preparation uses `user.id` for agent/MCP checks and thread resolution (`src/octop/api/routers/chat/turn.py:226-265`); inbound construction sets `ChannelSubject.subject_id=str(user_id)` from the server argument (`:306-353`). Client `UserTurnWsFrame` has no user/role field (`src/octop/api/routers/chat/models.py:143-166`). Thus the HTTP adapter has a sound source for the actor; the subject ID itself is only a value, not proof once detached from that adapter.
- Steer queue admission occurs after authenticated turn preparation (`ws.py:201-225`); direct cancel checks thread owner (`:150-177`), and steer removal receives `user.id` (`:179-187`). The HITL resume endpoint separately uses `current_user`, validates agent access, and resolves the pending card by `agent_id`, `thread_id`, and `user.id` (`src/octop/api/routers/chat/routes.py:242-280`). It passes that ID to bookkeeping/resume-drain code (`:289-303`), but `iter_hitl_resume_chunks` calls `AgentManager.resume_hitl(agent_id, thread_id, decisions)` without actor (`src/octop/infra/gateway/process/processor.py:1299-1327`). The nested auto-approve resume lambda likewise carries no actor (`:1188-1194`).
- Session-key resolution deserves a guard: `turn.session_key` is accepted from the client and used to look up a bound thread; the bound-thread return at `turn.py:68-86` does not re-check that row’s `user_id`. Explicit `thread_id` does check ownership (`:69-75`). An actor/thread binding must validate ownership on both resolution branches.

## Gateway and harness execution

- There are two processor entry points: IM/gateway `GlobalProcessor.__call__` (`processor.py:642-658`) and raw-chunk `iter_turn_chunks` for Dashboard/CLI/Agent MCP (`:946-979`). Both derive a numeric `user_id` through `resolve_user_id_for_message`. For dashboard/CLI/MCP this parses `ChannelSubject.subject_id`; otherwise it falls back to the agent owner (`message_keys.py:81-108`). The generic resolver cannot establish provenance by itself.
- Both paths build requests and reach `AgentManager.stream`: IM uses `project_stream` (`processor.py:833-887`, `stream_project.py:229-242`); raw stream uses `iter_turn_chunks` (`processor.py:1187-1195`). `AgentManager.stream`, `.call`, and `.resume_hitl` are the common harness seam (`src/octop/infra/agents/manager.py:1854-1914`), but their signatures accept no trusted actor. Harness request `user` is a string (`src/octop/infra/gateway/process/harness_request.py:293-354`), and team peer request copying can preserve that field (`src/octop/infra/agents/teams/team_manager.py:1642-1666`); neither should be used to mint `PluginActor`.
- IM principal IDs are platform subjects; Octop deliberately assigns these turns to the agent owner (`message_keys.py:86-108`). This is not an employee actor. A required enterprise binding must fail closed for IM unless a separately trusted identity mapping exists.

## Other routes and bypass assessment

- Agent MCP is authenticated with `current_user` (`src/octop/api/routers/agent_mcp.py:33-55`); `call_expert` constructs the MCP inbound from `user.id` and calls `iter_turn_chunks` (`src/octop/infra/agent_mcp/service.py:57-90`), and resume is scoped to that user (`:92-129`). It can supply an actor at ingress, but the generic processor/harness seam currently drops the proof.
- `internal_mcp` authenticates a connector’s internal token and forwards requests to connector/QCC handlers (`src/octop/api/routers/internal_mcp.py:50-96`); it is not an employee-authenticated chat ingress and has no actor to inject. Do not treat that connector token as a plugin actor.
- Bridge’s dashboard origin authenticates a JWT and verifies connection ownership (`chat/ws.py:45-57, 367-373`). However, the relay sends turn fields without the origin user ID (`src/octop/infra/bridge/manager.py:2075-2099`); the receiving peer resolves the bridge connection’s saved `owner_user_id` into a local user (`:1575-1607`) and builds the inbound using that user (`:1643-1667`). This proves the peer connection owner, not the initiating employee across instances. Required binding must reject unless an explicit trusted cross-instance actor mapping is introduced.
- Team/child turns bypass gateway processor entry points: `TeamManager.stream_peer_to_room` calls `AgentManager.stream` directly and resumes directly (`src/octop/infra/agents/teams/team_manager.py:452-520`). The peer request carries ordinary harness request fields, not a trusted actor. Internal ask_agent/HITL paths therefore need actor propagation or must reject required-bound execution. Cron also calls `AgentManager.stream` directly (`src/octop/infra/cron/delivery.py:150`), so non-human execution must remain allowed for unbound agents and fail closed only when the required binding applies.

## Smallest guard seam

Keep the Dashboard adapter as the trusted source: construct immutable `PluginActor` from the resolved `User`, then carry it in a server-only turn execution context (not client payload, `plugin_context`, writable business rows, or request `user`). Enforce required-extension presence and actor availability at the common execution boundary covering `AgentManager.stream`, `call`, and `resume_hitl`, and propagate the same actor through steer/HITL continuations and team-child calls. Add ingress guards at dashboard user_turn/steer/resume and any independently authenticated API action; they prevent untrusted requests entering queues, while the common boundary catches direct IM/Bridge/team/cron/CLI paths.

If a required extension is not bound, preserve current ordinary-agent behavior. If it is bound but the path cannot prove an actual user actor, reject only that enterprise-bound invocation before Harness execution. Do not infer actor from numeric channel subject, agent owner, `request.user`, bridge connection owner, or IM sender ID. Current `PluginActor` is only a DTO (`src/octop/infra/agents/plugins/host_contracts.py:21-35`); source search found no runtime construction/injection path, and Host currently only registers actions/resources/services (`src/octop/infra/agents/plugins/host.py:198-250`).
