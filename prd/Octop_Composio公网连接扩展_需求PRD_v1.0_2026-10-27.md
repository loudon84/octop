## 1. 目标、已确认决策与范围

### 1.1 产品目标

用户在 Octop 的连接器页面连接个人 Composio，完成外部应用授权，并在对话中显式选择后调用相关能力。页面应明确连接来源、账户归属、授权状态与使用范围，保留 Octop 内置连接器和自定义 MCP 的现有能力。

成功标准是一个完整闭环：个人登录授权 → MCP 连通 → 发现应用能力 → 应用授权 → 对话真实调用 → 停用或断开后无法继续新调用。

### 1.2 决策记录

| 决策 | 本期要求与原因 |
| --- | --- |
| 账户模式 | 每位 Octop 用户连接自己的 Composio 账户；不要求普通用户配置公司统一项目 API Key |
| 部署模式 | 接入 Composio 公网服务；私有化、VPC 和自托管不在本期范围 |
| 接入候选 | 优先验证 Composio Connect 个人 MCP 路径；官方公开地址为 `https://connect.composio.dev/mcp` |
| 页面组织 | 在连接器页面新增独立的“Composio 云应用”入口，与“Octop 内置”和“自定义 MCP”并列 |
| 账户数量 | 首期每个 Octop 用户最多绑定一个 Composio 连接；允许断开后重连 |
| 隔离与共享 | 个人连接不得共享；管理员不因管理身份自动取得使用他人连接的权限 |
| 工具选择 | 首期按整个 Composio 连接选择是否用于本轮；不承诺按应用隔离 |
| 默认使用 | 新建连接默认不随每次对话自动携带；首期不开放 Composio 的默认开启开关 |
| 目录策略 | 先提供已确认信息与搜索；完整应用目录、全量账户同步须有接口验证依据 |
| 凭证回传（v1.1） | Composio 授权回调在服务端直接保存凭证，浏览器不经手 token；其他目录类 OAuth 连接器（Notion、Ardot 等）维持现状，问题单独记录，不在本期修复 |
| 共享智能体隔离（v1.1） | 本期修复连接器运行时，使连接器解析、工具加载与缓存按“实际调用者 + 本轮”隔离；共享专家可安全使用调用者自己的 Composio 连接 |
| 管理员权限（v1.1） | 管理员对他人的 Composio 连接只能查看脱敏状态与强制断开；不能共享、发起授权、修改配置或代为调用，由后端按连接类型拒绝 |
| 页面应用管理（v1.1） | 保留页面内应用搜索与应用授权为 P0；后端以当前用户的个人连接调用 Composio 元工具实现，须先在 V-04 区分只读查询与会发起授权的调用 |
| 账户身份（v1.1） | 若 V-05 证实 id_token 或 userinfo 能返回 Composio 账户邮箱且与当前连接绑定，则将其作为可信远端身份展示 |

“每人最多一个 Composio 连接”不等于“每个外部应用只允许一个账户”。用户在 Composio 上可能已有多个 Gmail 等账户；首期必须核实其账户选择机制，无法确定时不能宣称 Octop 已固定使用某个邮箱。

### 1.3 方案比较

| 方案 | 收益 | 约束 | 结论 |
| --- | --- | --- | --- |
| 个人 Composio Connect + Octop 原生页面 | 符合用户已有个人账户使用方式，复用 MCP 接入 | 需验证 OAuth、账户信息及个人连接的可管理能力 | 本期选择的产品方向，先通过技术验证 |
| 公司统一 Developer Platform 项目 + 每用户 session | 项目接口、工具限制和应用目录更容易统一管理 | 账户、计费和资源归属与个人 Connect 不同 | 不在本期实施；若个人路径不成立，提供差异供用户重新决策 |
| 仅让用户手工添加通用 MCP | 改动少，可用于技术探测 | 缺少专用入口、个人账户生命周期和清晰的使用说明 | 可复用底层机制，不作为最终产品交付 |

### 1.4 非目标

- 不部署 Composio 服务，不接入 Arcade 或其他新平台。
- 不改造 Octop 的 LLM Provider、渠道或插件市场；Composio 属于工具连接来源。
- 不承诺所有公开网站均可连接；仅以 Composio 实际支持且当前用户获授权的应用能力为准。
- 不在首期建立按应用、按动作的权限编辑器，不提供无法在执行端强制落实的开关。
- 不实现 Composio 触发器、Webhook 任务、远程 Workbench/Bash 的专用产品界面。
- 不自动导入、迁移或合并用户的现有 Notion、邮箱等原生连接。

## 2. 现状与命名

当前连接器页面有“已启用、内置、自定义”三个页签。内置应用支持远程 MCP、stdio、进程内 gateway 和 internal HTTP MCP；自定义 MCP 已支持 HTTP URL、headers、OAuth 发现和凭证刷新等基础机制。已有用户归属、共享、默认开启、按轮加载与工具缓存逻辑可作为实施基础。

这些基础机制不代表 Composio 已兼容，更不代表所有凭证预览、共享入口和工具缓存可以直接照搬。实施者必须检查它们是否满足本文的个人隔离及脱敏要求。

### 2.1 “内置”与“内网”分别表达什么

| 术语 | 定义 |
| --- | --- |
| Octop 内置 | 由 Octop 维护接入适配的连接器，其上游也可能位于公网 |
| Composio 云应用 | 经个人 Composio 公网连接使用的应用能力 |
| 自定义 MCP | 用户自行配置服务器地址或本地进程的 MCP 连接 |
| 内网／公网 | 实际服务的网络位置，与连接器来源不是同一分类 |

页面不能把现有内置连接器统一标为“内部应用”。同一个服务通过不同来源接入时，保留独立记录并显示来源。

### 2.2 三个产品对象

1. **Composio 连接**：当前 Octop 用户与个人 Composio 之间的授权及 MCP 连接，首期可运行和可选择的单位。
2. **应用**：例如 Gmail、GitHub，对应可发现的一组能力，不等于已取得授权。
3. **应用账户**：某个实际授权账户。其状态与名称只能由可靠的上游响应确认。

### 2.2.1 源码核查发现（v1.1，基线 `69d50fdd`）

可复用的部分：目录连接器已支持“`oauth_issuer` + `mcp_url`”的远程 MCP OAuth（RFC 8414 发现、动态注册、PKCE、刷新），见 `infra/connectors/oauth/mcp.py` 与 `catalog.json` 中的 Notion、Ardot、Dida 条目。`host_allowed_for_issuer` 按根域放行，Composio 的 `login.composio.dev` 端点可以通过 issuer `connect.composio.dev` 的校验。Composio 连接应以目录类型 `composio-connect` 复用这条链路。

以下现有行为与本文要求冲突，Composio 上线前必须解决：

| 编号 | 现状 | 位置 | 本期要求 |
| --- | --- | --- | --- |
| A | 目录类 OAuth 回调把完整 token 以明文写入 `settings` 的 `connector.oauth.pending.*`，前端轮询接口原样返回给浏览器 | `api/routers/connectors.py` 回调与 pending 轮询 | Composio 在回调中直接加密保存并只返回脱敏结果；其他目录连接器另行记录 |
| B | `_can_manage_connector` 允许管理员管理任何连接，可写 `shared`；`list_visible` 以 `OR shared = 1` 让共享连接对所有用户可用 | `api/routers/connectors.py`、`infra/db/repos/connectors.py` | `composio-connect` 永不可共享；管理员只能查看与强制断开（§6） |
| C | 共享智能体以 `_connector_user_override[agent_id]` 记录当前调用者，并通过 `_reload_agent` 为整个智能体挂载单一用户的工具；同一智能体的并发调用会互相覆盖 | `infra/agents/manager.py` | 改为按调用者与本轮隔离（§6） |
| D | `consume_oauth_state` 只做单次消费，不校验有效期；过期事务只靠定期清理 | `infra/db/repos/connectors.py` | 消费时校验有效期，过期视为无效 |

另需在 M1 实测：MCP 工具缓存键 `(user_id, server_name, fingerprint)` 的 fingerprint 是否随凭证版本变化；回调错误页是否会输出上游响应片段。

## 3. 用户与使用场景

| 角色／场景 | 预期行为 |
| --- | --- |
| 用户首次接入 | 在 Composio 页完成个人授权，返回后看到真实连接状态 |
| 用户连接应用 | 搜索所需应用，打开对应授权链接，完成后检查状态 |
| 用户执行任务 | 对话中选择“我的 Composio”，由智能体发现并使用获授权的应用工具 |
| 用户临时停用 | 暂停 Octop 使用该连接，保留授权以便恢复 |
| 用户退出绑定 | 从 Octop 断开连接，不自动撤销其在 Composio 中的其他应用授权 |
| 多用户使用共享专家 | 每轮按实际调用者取连接，不沿用另一人的已加载工具或凭证 |
| 管理员维护系统 | 可诊断服务故障，不通过后台查看个人凭证或代用个人授权 |

## 4. 页面需求

### 4.1 页签与信息架构（P0）

连接器页面调整为：**已连接｜Octop 内置｜Composio 云应用｜自定义 MCP**。

- “已连接”统一展示已经建立配置记录的连接，包括停用或需要重新授权的连接；每条状态必须可见。
- Composio 在“已连接”列表中按一个个人连接计数，不把每个应用视图重复计为可运行连接器。
- Composio 卡片显示来源、个人归属、状态和“管理”入口；点击进入 Composio 页。
- 保留现有内置和自定义 MCP 的配置、共享及对话选择行为；Composio 执行本文的特殊限制。
- 页面链接、刷新、授权回跳后应保持在对应页签。

### 4.2 个人 Composio 账户区（P0）

| 状态 | 页面内容 | 可用操作 |
| --- | --- | --- |
| 未连接 | 用途说明、个人授权说明 | 连接我的 Composio |
| 授权中 | 等待授权、授权链接有效性说明 | 继续授权、取消本次流程 |
| 已连接 | 连接名称、来源、最近检查时间、连接状态 | 检查连接、管理应用、停用、断开 |
| 需要重新授权 | 说明个人 Composio 连接授权已失效 | 重新授权、断开 |
| 暂时不可达 | 展示可恢复错误及上次检查时间 | 重试、停用、断开 |
| 已停用 | 说明不会被 Octop 新调用 | 恢复、断开 |

若 V-05 证实授权返回的 id_token 或 userinfo 含有 Composio 账户邮箱，且该身份与当前连接的凭据绑定，则显示该邮箱并标注来源为 Composio；账户更换后必须以新凭据重新取得。未取得可信账户标识时，显示用户自定义的连接名称或“我的 Composio”；不得把 Octop 登录邮箱当作 Composio 账户身份。账户身份未知时也不能宣称已验证两个授权属于同一远端账户。

普通用户不填写上游 endpoint、issuer、项目 API Key 或底层 headers。固定入口由后端控制，敏感凭证由受支持授权流程取得；兼容性不足时先记录阻塞，不增加临时密码粘贴方案绕过。

### 4.3 我的应用与发现应用（P0 基础、P1 完整目录）

- “发现应用”允许按应用名或任务描述搜索，展示实际返回的名称、说明及可确认的能力。
- “我的应用”只列出已从上游确认的应用／账户；若只能取得局部信息，应明确“已确认应用”，不能表达为全量清单。
- 上游只能按需搜索时，采用搜索式入口，空白处给出搜索提示；不得抓取未公开页面、维护虚假全量目录或要求统一项目 Key 补足个人账户信息。
- 搜索结果必须保留真实 toolkit／工具标识，不根据名称自行生成上游 slug。
- 无需账户授权的工具可说明“无需授权”，不能误标“我的账户已连接”。
- 目录信息和授权状态分开缓存；目录存在不意味着用户已连接。
- 页面初始加载、搜索和授权状态刷新不得自动触发业务写操作。
- 分页目录、分类筛选、完整账户列表仅在第 9 节验证支持时纳入 P1。

### 4.4 应用详情（P0）

详情抽屉显示应用说明、来源“Composio”、可确认的账户信息、授权状态与更新时间，提供经验证支持的“连接”“继续授权”“重新授权”“检查状态”。

首期不显示“仅允许此应用”“禁用此应用”“只读访问”等权限开关，除非执行端可以强制执行且通过负例验证。不得通过前端隐藏应用或提示词模拟权限。应用详情中的已授权账户不能直接变成对话选择器的应用级授权边界。

### 4.5 文案与云服务告知（P0）

建议在首次授权及详情页提供简短说明：

> 连接你的个人 Composio 账户，通过 Composio 云服务使用外部应用。相关工具请求与结果会经过 Composio；应用授权在 Composio 或对应应用的页面完成。

对话选择器说明：

> 本轮允许使用我的 Composio 连接；可访问范围取决于 Composio 账户及应用授权，不仅限于此页面展示的应用。

不把“凭证未交给模型”表述成“业务数据不出网”。连接器有外部服务依赖，失败时显示可操作提示；不展示未经账户核实的费用、免费额度或订阅状态。

所有新增文案提供中英文；时间按服务器 `default_timezone` 显示。

## 5. 核心流程与状态

### 5.1 连接个人账户

1. 当前用户点击“连接我的 Composio”，后端创建属于该用户的一次性授权事务。
2. 使用实际支持的 MCP OAuth 发现和注册／授权方式，跳转至 Composio 登录授权页面。
3. 校验回调及事务归属与有效期，后端在回调中直接加密保存个人 MCP 凭据；回跳页面和轮询接口只返回脱敏结果，不复用现有目录连接器“token 交前端再提交”的流程（§2.2.1-A）。
4. 完成 MCP 初始化与工具列表检查后，才能显示连接可用；仅收到 OAuth code 不能作为成功依据。
5. 返回 Composio 页；刷新、浏览器重启或服务重启后能够恢复已保存连接。

取消、超时、重复回调和失败回调不得覆盖现有可用连接。重复点击不得建立多个活动连接；更换账户必须使旧连接的缓存、授权事务和待执行引用失效，不能让旧回调重新恢复旧身份。

### 5.2 连接外部应用

1. 用户从搜索结果或应用详情发起连接。
2. 通过当前用户的 Composio 连接取得真实授权链接；普通状态检查不得无意创建或重置授权。
3. 浏览器完成授权，Octop 在有限等待后检查结果；用户可离开页面后再次检查。
4. 只有上游证据确认可用后显示“已授权”；单纯回跳或用户点击“我已完成”不构成验证。
5. 页面无法查询完整状态时显示“状态待检查”，允许用户使用已验证的官方管理入口；不伪造成功。

如上游接口将“查询”与“发起授权”合并，必须先验证实际语义，再将此调用放在明确的用户动作后执行。

页面内的应用搜索与授权由后端以当前用户的个人连接调用 Composio 元工具实现（v1.1 决策）。V-04 必须列出所用元工具及参数，并逐一标注“只读查询”或“可能发起／重置授权”；后者只能挂在明确的用户按钮上，不得用于页面加载或状态轮询。

### 5.3 对话调用

1. 用户在现有对话连接器选择器中勾选“我的 Composio”。
2. Octop 检查该用户连接归属、启用状态和凭据有效性，再按需加载 MCP 工具。
3. 智能体根据请求发现并使用上游应用能力；需要授权时向用户展示授权链接，不绕过授权。
4. 工具调用记录应标明来源 Composio；上游响应有实际应用／工具标识时一并展示，不能只记录一次外层搜索就宣称业务执行成功。
5. 用户取消本轮选择、停用或断开后，后续新调用不得继续使用之前加载的工具或客户端。

首期默认不开启自动携带。Dashboard 明确勾选后使用；IM 和 Cron 仅在已有、受支持的显式选择机制下使用，不额外实现新交互，也不因为默认配置合并而自动获得 Composio。无人值守任务遇到授权要求应停止相关调用并提示待授权，不无限等待。

### 5.4 停用与断开

| 操作 | 本地效果 | 对 Composio 的效果 |
| --- | --- | --- |
| 停用 | 保留加密凭据，拒绝后续新调用，清理已加载工具／缓存 | 不自动变更远端应用授权 |
| 恢复 | 检查连接后允许再次显式选择 | 可能需要重新授权，以真实结果为准 |
| 从 Octop 断开 | 删除或失效化本地绑定、凭据、授权事务及工具缓存 | 不自动删除其他客户端使用的应用连接 |
| 撤销远端授权 | 非首期独立管理功能；可指引至已验证的官方管理入口 | 与本地断开不是同一个动作 |

断开确认文案应明确本地影响。已被上游接受的业务操作不能承诺撤回；对超时的发送、创建等写操作不能自动重试并宣称第一次未执行。

### 5.5 分层状态模型

| 层级 | 建议状态 | 不得混淆的语义 |
| --- | --- | --- |
| 个人连接认证 | disconnected / authorizing / authenticated / reauth_required | 认证成功不代表应用已授权 |
| 连接健康 | unknown / reachable / unavailable | 暂时网络失败不自动删除凭证 |
| Octop 使用 | enabled / disabled | 具有凭证不代表当前允许调用 |
| 应用授权 | unknown / not_connected / authorizing / authorized / reauth_required | 必须有与当前个人连接匹配的上游证据 |
| 本轮选择 | selected / unselected | 不修改持久授权状态 |

最终字段名可随现有接口约定调整，但各维度必须保留。没有确认的应用状态使用 unknown；不得把“上次已授权”的过期缓存展示成实时正常。

## 6. 个人隔离、凭证与执行要求（P0）

- 所有个人连接、回调、应用状态、工具加载、刷新与调用操作，均由服务端根据当前已认证用户校验归属；不信任客户端传入的 `user_id`。
- 同一 MCP URL 不意味着同一用户。缓存和 MCP 客户端至少按用户、连接实例和凭证版本／失效代次隔离；账户切换、刷新、停用和断开应按需失效化。
- 首期禁止共享个人 Composio；隐藏共享控件之外，后端也必须拒绝共享写入，通用 connector PATCH／导入路径不能绕过。可见性查询不得因 `shared` 标志把 `composio-connect` 暴露给 owner 之外的用户（§2.2.1-B）。
- 管理员对他人的 Composio 连接只允许两项操作：查看脱敏状态、强制断开。共享、发起授权、修改配置、代为调用一律由后端拒绝；现有“owner 或 admin 可管理”的通用判断不能直接套用。
- 共享专家和持续运行的智能体必须按实际调用者取连接；验证 A→B→A 连续调用及并发情形，不沿用上一次用户状态。本期修复 §2.2.1-C：连接器用户解析、工具挂载与缓存不得以 `agent_id` 为唯一键保存“当前用户”，应随本轮调用携带调用者身份；先写复现并发串用的失败测试，再修改实现。该修复覆盖所有连接器，须对既有内置和自定义 MCP 做回归。
- 复用既有加密存储；token、refresh token、认证 headers、授权 code、完整一次性授权链接及 PKCE verifier 不写入普通日志、前端持久存储或模型上下文。
- OAuth 凭据与 headers 不能经连接详情、列表、导出、错误信息或通用自定义 MCP 查询泄露；仅允许返回脱敏状态。
- 校验 OAuth state、PKCE、有效期、单次消费、redirect_after 和事务归属；错误用户或重放回调不能绑定连接。有效期在消费时校验，不依赖定期清理（§2.2.1-D）。
- 使用固定 HTTPS MCP 入口；授权发现可使用合法的不同 issuer，但不能把 MCP 认证 headers 随重定向发送给其他 origin。遵守现有出站 URL 安全校验。
- Composio 作为元工具入口可能触达多个应用；首期不能声称本地应用卡片是服务端应用白名单。未来如增加按应用限制，必须覆盖搜索、批量执行、间接调用及远程执行等路径。
- 未经独立产品要求，不主动向用户开放远程 Bash／Workbench 专用入口。实际 MCP 工具列表及是否可在保持正常调用的前提下缩减暴露，在技术验证中记录；不把未过滤的连接宣传为“只读工具”。

## 7. 实现边界与建议契约

### 7.1 模块职责

| 层 | 职责 |
| --- | --- |
| `dashboard/src/pages/Agent/Connectors/` | 页签、账户卡片、搜索、应用详情、授权返回状态 |
| `dashboard/src/api/modules/connectors.ts` | 类型化接口调用；页面不直接请求 Composio 的敏感接口 |
| `src/octop/api/routers/connectors.py` 或同级薄路由 | 当前用户鉴权、请求校验、调用领域服务、错误映射 |
| `src/octop/infra/connectors/` | Composio 连接生命周期、能力检测、应用搜索／授权、状态归一化 |
| `infra/connectors/oauth/` | 复用 OAuth 发现、PKCE、授权及刷新机制，补充必要兼容 |
| `infra/agents/manager.py` 现有连接器入口 | 按实际用户加载、选择、刷新、缓存失效与执行隔离；修复 §2.2.1-C 的按智能体保存调用者问题 |
| 既有 connector repo／服务 | 持久化个人连接；SQL 与业务编排分层 |

使用目录连接类型 `composio-connect`（`auth_kind=oauth2`，`oauth_issuer=https://connect.composio.dev`，`mcp_url=https://connect.composio.dev/mcp`），底层复用 MCP 协议及既有凭证生命周期。不要同时在内置和自定义 MCP 中创建两个可运行副本，也不要为了一个来源提前重构成通用连接器平台。

复用现有机制前检查其脱敏、共享与 owner 语义，不直接沿用可能返回敏感 headers 的通用配置预览。新增 API 保持 typed request／response、summary、现有错误码与国际化约定。

### 7.2 对外操作契约

以下是 Octop 应提供的逻辑操作；最终 URL 在实施设计中确定，尽量复用已有路由而不破坏兼容。

| 操作 | 行为要求 |
| --- | --- |
| 读取个人连接 | 返回脱敏账户名称、分层状态、能力标志、最近检查时间 |
| 开始／完成授权 | 由服务器创建用户事务和保存凭据；回调后验证 MCP 可用性 |
| 检查连接 | 无业务副作用地检查连通与认证，返回真实结果 |
| 停用／恢复／断开 | owner 校验，执行状态及缓存失效，保持远端授权语义明确 |
| 搜索应用能力 | 调用经过验证的个人接口，返回上游真实标识与能力说明 |
| 开始应用授权 | 明确用户动作后取得一次性链接，不通过页面初始加载触发 |
| 检查应用状态 | 只返回可验证的信息；不支持的能力明确返回 unavailable／unknown |

能力标志至少表达是否支持完整目录、列出个人应用、读取账户身份、检查授权状态。它们描述适配器确认的能力，不由前端猜测，也不直接反映“已连接”。

### 7.3 数据最小集

个人连接至少保留：公开实例 ID、owner、来源、显示名称、启用状态、认证状态、加密凭据、最近检查时间及凭据失效代次。允许复用现有字段／元数据，不要求为每个概念新建表。

如持久化应用视图，至少关联个人连接 ID、上游 toolkit 标识、可确认的账户标识、状态、信息来源及检查时间。账号未知、状态未知都必须允许，且不将搜索结果当作授权记录。

需要数据库变更时遵守根目录 AGENTS.md 的 SQLite／PostgreSQL 成对迁移、未发布迁移折叠与公开字符串 ID 规则；不得机械按文档旧版本号新增迁移。

## 8. 异常与恢复

| 情形 | 产品行为 |
| --- | --- |
| 用户取消或关闭授权窗口 | 保持未完成；可重开有效流程，不伪造成功 |
| 授权链接过期 | 提示重新发起，不重复使用过期链接 |
| 页面刷新／服务重启 | 恢复持久连接；未完成事务按有效期恢复或过期 |
| MCP 初始化失败 | 展示认证／协议／网络错误类别，不仅凭存有 token 显示正常 |
| token 刷新失败 | 标为需要重新授权，停止新调用，不影响其他用户 |
| 上游限流／暂时故障 | 有界重试读取并尊重上游提示；不重试不确定的业务写入 |
| 目录／账户信息不支持 | 降级为搜索与状态待检查，保留已验证的连接能力 |
| 一个应用授权失效 | 标记该应用问题，不把所有 Composio 连接直接判为失效 |
| 用户更换 Composio 账户 | 清除旧身份缓存、应用视图和授权事务，重新检查 |
| 外部应用名与内置连接重名 | 显示来源与账户，保持独立标识 |

网络、授权与上游业务失败应分类呈现；不向普通用户输出堆栈、完整认证 URL 或敏感 payload。

## 9. 实施前技术验证与停止条件

### 9.1 验证要求

使用操作者控制的测试账户和合成数据。测试所需真实授权由账户持有人完成，不索取密码或将 token 粘贴到仓库。记录日期、Octop／依赖版本、请求类型、结果与脱敏证据；不把长期凭证写进报告。

| 编号 | 验证项 | 必须产出的判断 |
| --- | --- | --- |
| V-01 | Connect 是否允许当前 Octop 客户端注册和授权 | discovery、注册方式、issuer、受支持 callback 与部署条件 |
| V-02 | 登录后 MCP initialize、tools/list 和刷新 | 实际工具 schema、登录保持方式、重启与过期行为 |
| V-03 | 两个个人账户互相隔离 | Octop A/B 的授权与真实调用不会串用 |
| V-04 | 应用搜索与授权 | 当前个人凭据下可用的搜索、授权链接、状态检查方法 |
| V-05 | 目录、应用列表与账户身份 | 每项标记支持／局部支持／不支持，记录真实接口与样例 |
| V-06 | 多应用账户、元工具及远程执行 | 账户选择是否可确定、实际暴露范围、可过滤范围和限制 |
| V-07 | Octop 部署的回调可达性 | localhost、现有 HTTPS 入口及远程访问场景；按实际授权链路确认，不默认要求把内网 Octop 公开到互联网 |

V-05 须额外确认：id_token 或 userinfo 是否返回账户邮箱、该邮箱是否与本次凭据绑定、账户更换后是否随之变化。

### 9.1.1 V-01 匿名探测结果（2026-10-27，未登录任何账户）

| 请求 | 结果 |
| --- | --- |
| `GET /.well-known/oauth-protected-resource` | 200；`resource=https://connect.composio.dev/mcp`，授权服务器 `https://connect.composio.dev`，bearer 仅支持 header |
| `GET /.well-known/oauth-authorization-server` | 200；authorize 在 `connect.composio.dev`，token、register、jwks 在 `login.composio.dev`；PKCE 仅 `S256`；token 端点认证方式仅 `none`（公共客户端）；scope 为 `openid profile email offline_access` |
| 未带凭证 `POST /mcp` | 401；`WWW-Authenticate` 指向上述 protected-resource 元数据 |

结论：发现与动态注册的前提条件满足，与 Octop 现有 MCP OAuth 实现的端点校验兼容。注册是否接受 Octop 的回调地址、授权、MCP initialize 与刷新仍须真实账户完成 V-01 后半段与 V-02。

V-01～V-04 的核心链路是 P0 前置条件。V-05 不支持时按第 4 节降级，不能因此改用公司项目 Key。V-06 中无法确定的细粒度控制从首期界面移除，保留整条连接使用范围告知。

官方对应用开发推荐 SDK／session，而个人客户端提供 Connect。技术验证必须确认这条个人客户端路线适合 Octop 的实际多用户部署、客户端注册及使用条件；公开有 MCP 地址不能替代兼容性验证。

### 9.2 停止条件

如果个人 Connect 无法完成合法授权、无法区分用户、无法持久恢复或不支持 Octop 这种客户端接入，暂停依赖它的功能交付。输出明确证据、失败环节和替代方案差异，向用户提出需要决策的问题。

不得用管理员个人账户共享、抓取 Composio 网页 cookie、伪造账户状态、硬编码 token、悄悄接入 Developer Platform 项目等方式宣布完成。协议兼容问题应先在既有授权流程内修复；只有确实需要改变已确认产品方向时才回到用户决策。
